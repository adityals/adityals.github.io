Moving a large frontend monorepo from Webpack to Rspack

Platform · Led, built solo · 2024–2026

  • CI build, 4 CPU65 → 11 min
  • CI build, 7 CPU62 → 4 min
  • Build memory−30–40%
Problem
The largest codebase in the web monorepo serves every internal tool in the company. A build and deploy took over an hour, which slowed each release and ran up CI spend.
My role
I led the migration and wrote it alone. In 2026 I ran the same cutover on the client build of the company's in-house web framework.
Decisions
The Webpack builds depended on custom Babel transforms. I ported them to SWC plugins in Rust so application code stayed untouched. I published the config to the whole monorepo, and for the framework I designed the cutover plan and the toolchain's config surface.
Result
CI builds dropped 84% with zero app code changes. A second team adopted the config on their own and went from 22 minutes to 1. On the framework, large services no longer need --max-old-space-size=8092, and three high-traffic services now build 10–15× faster.
Stack
Rspack · SWC · Rust · Webpack · Babel · TypeScript

Isolated preview deploys for 50 frontend engineers

Platform, full stack · Co-lead · 2022–2023

  • 50 engineers onboarded
  • ~60 preview deploys a day
Problem
Each domain had one shared staging environment. Engineers testing features overwrote each other's deploys and waited in line for a clean slot.
My role
I co-led the platform, led one engineer, and built the API and the UI.
Decisions
A Go API on Chi accepts a preview request and hands it to workers over NSQ, so slow builds never block the API. GitHub Actions does the build work: it bakes a Docker image, and Terraform provisions one Cloud Run service per preview. A React UI lists, opens, and tears down previews.
Result
Every feature branch got its own domain, close to how Vercel previews work. The company retired the platform after an acquisition moved the web stack elsewhere.
Stack
Go · Chi · NSQ · GitHub Actions · Terraform · Docker · Cloud Run · React

Smaller, faster fintech web apps

Product frontend · Main developer · 2021–2022

  • JS budget300 → <200 KB
  • Initial load−30%
  • Mobile Lighthouse~40 → ~80
Problem
Five fintech web apps ran on a legacy React stack with no tests. Four product landing pages loaded slowly on mobile.
My role
Main developer on both the app rewrite and the landing pages, plus the Koa server layer behind them.
Decisions
I rewrote class components as hooks, swapped Redux for context with reducers, and replaced moment with dayjs. The apps moved to a new build toolchain and Emotion. On the landing pages I turned on SSR, lazy-loaded everything below the fold, and deleted dead code that JS coverage reports exposed.
Quality
The apps started with zero tests. I covered every critical path and business rule with Jest before changing behavior.
Stack
React · TypeScript · Emotion · Node.js · Koa · Jest
